## Архитектурные баги (февраль 2026)

### БАГ #1: ECS Entity Pending Addition не обрабатывается
**Severity:** CRITICAL
**Status:** Открыто
**Location:** `nine/core/ecs.py:445-470`
**Обнаружен:** 2026-02-01 (комплексное тестирование NPC AI)

**Описание:**
Entities созданные через `world.create_entity()` добавляются в `_pending_addition` очередь и НЕ доступны для `get_entities_with_components()` до явного вызова `world.update()` или `_process_pending_additions()`. Это делает тесты непредсказуемыми и может вызывать баги в runtime.

**Воспроизведение:**
```python
world = ECSWorld()
npc = world.create_entity()
npc.add_component(PositionComponent())

# БАГ: entities пуст, хотя entity создан!
entities = list(world.get_entities_with_components(PositionComponent))
# len(entities) == 0 вместо ожидаемого 1
```

**Влияние:**
- Unit-тесты не могут проверить entity сразу после создания
- Запросы к ECS World могут возвращать пустые результаты
- Нарушение принципа наименьшего удивления (Principle of Least Astonishment)

**Решение:**
- **Вариант A:** Автоматически вызывать `_process_pending_additions()` в конце `create_entity()`
- **Вариант B:** Сделать `get_entities_with_components()` проверять pending_addition
- **Вариант C:** Документировать это поведение и добавить метод `flush_pending()`

**Детали:** См. `/home/mrv/Homework/PROJECTS/niNE/NPC_BUG_REPORT.md` (Баг #1)

### БАГ #2: AISystem требует жесткую связь с NPCManager
**Severity:** HIGH
**Status:** Открыто
**Location:** `nine/plugins/npc/sv_npc_ai.py:382-383`
**Обнаружен:** 2026-02-01 (комплексное тестирование NPC AI)

**Описание:**
AISystem не может работать без NPCManager - при отсутствии NPCManager метод `_update_player_cache()` делает ранний возврат, оставляя кэш игроков пустым. Это делает систему **не unit-testable** и нарушает принципы декаплинга.

**Код:**
```python
def _update_player_cache(self) -> None:
    if not self.npc_manager:
        return  # <-- ранний возврат, player cache остается пустым
```

**Влияние:**
- NPC не видят игроков в unit-тестах
- **СВЯЗАНО С ПРОБЛЕМОЙ:** "Бой начинается автоматически" (см. ниже) - без player cache AI не может корректно определить врагов
- Невозможно изолированно тестировать AI логику
- Нарушение Single Responsibility Principle

**Решение:**
- **Вариант A:** Инжектить список игроков через параметры `update(dt, player_positions=None)`
- **Вариант B:** Сделать player detection опциональным (если игроков нет, AI работает только с NPC)
- **Вариант C:** Создать отдельный компонент `PlayerDetectionComponent` для инжекции

**Детали:** См. `/home/mrv/Homework/PROJECTS/niNE/NPC_BUG_REPORT.md` (Баг #2)

### БАГ #3: FactionComponent обязателен для вражеской детекции
**Severity:** MEDIUM
**Status:** Открыто (требует документации)
**Location:** `nine/plugins/npc/sv_npc_ai.py:_find_nearest_enemy`
**Обнаружен:** 2026-02-01 (комплексное тестирование NPC AI)

**Описание:**
Метод `_find_nearest_enemy()` требует `FactionComponent` у всех entities, иначе возвращает `None`. Это поведение **НЕ документировано** и может привести к молчаливым багам.

**Код:**
```python
faction = entity.get_component(FactionComponent)
if not faction:
    return None  # <-- Без FactionComponent враг не детектится
```

**Влияние:**
- Игроки без `FactionComponent` невидимы для NPC AI
- Тесты не могут проверить логику без создания FactionComponent
- Сложность отладки (silent failure)

**Решение:**
- **Минимальное:** Документировать в docstring `_find_nearest_enemy()`
- **Рекомендуемое:** Сделать FactionComponent опциональным с дефолтным поведением (например, если нет FactionComponent - считать neutral)
- **Альтернатива:** Логировать warning при отсутствии FactionComponent

**Детали:** См. `/home/mrv/Homework/PROJECTS/niNE/NPC_BUG_REPORT.md` (Баг #3)

### UI System - Множественные проблемы наложения (январь 2026)
**Статус:** Открыто (отложено до полного рефакторинга UI)
**Приоритет:** Средний (не блокирует геймплей)
**Файлы:** `nine/ui/blocks.py`, `nine/ui/login_menu.py`, `nine/ui/settings_menu.py`, `nine/plugins/dnd/cl_character_select.py`

**Описание:** После тестирования обнаружено множество проблем с UI layout системой:
1. Имя персонажа в Settings вылазит за границы окна
2. Кнопки "Войти" и "Назад" в Login Menu налазят на поле ввода пароля
3. Кнопка удаления (X) в Character Select отображается как полоска вместо крестика
4. Общая проблема: элементы интерфейса налазят друг на друга по всему UI

**Причина:** Блочная система layout (`blocks.py`) имеет фундаментальные проблемы с расчётом позиций и размеров:
- `Row.build()` неправильно распределяет элементы по горизонтали
- `EntryElement.get_size()` не учитывает переменную ширину кириллических символов
- `Block.get_content_height()` неправильно суммирует высоты элементов
- Z-ordering не контролируется, элементы перекрывают друг друга

**Решение:** Полный рефакторинг UI layout системы (отложено):
- Заменить самописную блочную систему на Panda3D DirectGUI layout (DirectBoxSizer)
- Или реализовать CSS-подобную flexbox систему
- Добавить автоматическое определение overflow и scroll
- Добавить debug mode с подсветкой границ элементов

**Временное решение:** Использовать прямое позиционирование через BG1Button.create() вместо Block.row()

## Оптимизация NPC (для масштабирования 100-500+ NPC)

> **Цель:** Достичь уровня RimWorld/Kenshi — сотни NPC с индивидуальным поведением.
> **Текущая оценка:** ~20-50 NPC без оптимизации.

### AI Level of Detail (AI LOD)
- [ ] **Distant NPCs think less** — NPC далеко от игрока думают реже (раз в 2-5 сек вместо 0.5)
- [ ] **Offscreen NPCs** — NPC вне экрана используют упрощённую симуляцию
- [ ] **Sleep system** — NPC в неактивных чанках полностью "спят"

### Pathfinding оптимизация
- [ ] **Hierarchical A*** — двухуровневый pathfinding (грубый + детальный)
- [ ] **Path caching** — кэширование часто используемых путей
- [ ] **Flow fields** — для групп NPC идущих в одну точку
- [ ] **Async pathfinding** — расчёт путей в отдельном потоке
- [ ] **Path request throttling** — не более N запросов путей за тик

### Spatial Partitioning
- [ ] **Grid-based chunks** — мир разбит на чанки, обновляются только активные
- [ ] **Spatial hash** — быстрый поиск соседей для AI
- [ ] **Interest management** — клиент получает только nearby NPC

### Batching и Pooling
- [ ] **Entity pooling** — переиспользование Entity объектов
- [ ] **Component pooling** — переиспользование компонентов
- [ ] **Batched updates** — группировка обновлений (не каждый кадр)
- [ ] **Dirty flags** — обновлять только изменённые данные

### Network оптимизация
- [ ] **Delta compression** — отправлять только изменения позиций
- [ ] **Priority queue** — важные NPC (в бою) обновляются чаще
- [ ] **Area of Interest** — клиент получает только NPC в радиусе
- [ ] **Interpolation hints** — клиент предсказывает движение

### Rendering оптимизация
- [ ] **LOD models** — упрощённые модели для дальних NPC
- [ ] **Animation LOD** — дальние NPC используют упрощённые анимации
- [ ] **Instancing** — одинаковые модели рендерятся батчами
- [ ] **Culling** — не рендерить NPC за камерой/стенами
- [ ] **Billboard sprites** — очень дальние NPC как 2D спрайты

### Архитектурные улучшения
- [ ] **Job system** — параллельные обновления систем
- [ ] **Data-oriented ECS** — оптимизация под кэш CPU
- [ ] **C extension** — критичные системы (pathfinding, AI) на C/Cython
- [ ] **Профилирование** — найти реальные bottlenecks

### Целевые метрики
| Метрика | Цель |
|---------|------|
| NPC count | 300-500 одновременно |
| AI update | < 5ms на 100 NPC |
| Pathfinding | < 2ms на запрос |
| Network | < 50KB/s на клиента |
| Frame time | < 16ms (60 FPS) |
